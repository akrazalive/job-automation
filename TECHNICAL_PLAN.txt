0. LOCKED-IN DECISIONS (from requirements conversation)
------------------------------------------------------------
- Apply mode:        FULL-AUTO submit on LinkedIn & Indeed (no human click
                      before final submit). User explicitly accepted the
                      ban/CAPTCHA risk that comes with this. Mitigate with
                      rate limits + circuit breaker (see section 6), do not
                      silently drop these safeguards to "simplify" later.
- Language:           Python 3.11+
- Job sources v1:     LinkedIn, Indeed, SimplyHired
- Resume tailoring:   Reorder skills section + rewrite bullet PHRASING to
                      mirror JD keywords only. Do NOT touch company names,
                      titles, dates, education. Do NOT invent projects.
- Storage/hosting:    AWS Free Tier for storage/dashboard only (S3 +
                      DynamoDB + dashboard compute). The actual browser
                      automation (login/search/apply on LinkedIn & Indeed)
                      runs LOCALLY on the user's own machine/home IP, not
                      on AWS — see section 6. This is a deliberate
                      anti-ban decision, not a placeholder: AWS EC2 IPs
                      are known datacenter ranges that LinkedIn/Indeed
                      flag on their own, independent of timing/behavior.
                      Do not "simplify" this later by moving apply
                      automation to EC2 without re-confirming with the
                      user — it changes the risk profile.
- Report/admin view:  A dashboard the user can open to see: jobs found,
                      jobs applied (success), jobs failed (with a reason),
                      duplicates skipped. Filterable by site/date/company.
- Source resume:      "Full Stack Developer - Complete.docx" in repo root
                      (git-ignored — PII, never commit it or any tailored
                      copy). This is the input to digitize into
                      resume/master_resume.json in Phase 0/1.

PHASE 8 — Safety hardening & scheduling
  - Daily application cap per site (config value, e.g. 15/day/site).
  - Randomized delays between actions (a few seconds to a couple minutes,
    not fixed intervals — fixed timing is itself a bot signal).

    automation for N hours (config), log the run as "blocked", and surface

    site that's actively blocking us.
  - Alerting: simple email (SES free tier) or just a dashboard banner when
    a site gets blocked or the daily cap is hit.
  - Scheduling: cron (EC2) or Windows Task Scheduler (local) to run
    src/scheduler/run.py on an interval (e.g. every few hours).

6. SAFETY / ANTI-BAN NOTES (do not skip when implementing Phase 4/5)
------------------------------------------------------------
User explicitly chose full-auto submit and accepted the risk — that does
NOT mean skip the mitigations, it means these mitigations are the only
thing standing between "works for months" and "account banned week one".

IMPORTANT: delay length between actions is the SMALLEST factor in ban
risk, not the biggest. A fixed "wait 5-10 min then apply" scheme was
considered and rejected as insufficient on its own (see conversation
2026-09-08) — it only addresses the "search->apply->search->apply" loop
pattern. The real risk factors, ranked by impact, and what we do about
each:

  1. IP REPUTATION (biggest factor, independent of timing)
     AWS/EC2/any datacenter IP is itself a red flag to LinkedIn/Indeed
     regardless of how slow or human-like the behavior is. DECISION:
     browser automation runs on the user's LOCAL machine / home IP, not
     on AWS (see section 0/3). Do not change this without re-confirming.

  2. BROWSER FINGERPRINT (second biggest factor, independent of timing)
     Playwright/Selenium have detectable signatures (navigator.webdriver,
     headless quirks, missing Chrome-only APIs). Mitigate with:
     - playwright-stealth (or equivalent) patches
     - ONE persistent browser profile / storage_state.json reused across
       every run (a login session and fingerprint that stays consistent
       over time looks like a real returning user; a fresh fingerprint
       each run looks like a bot farm)
     - Never spin up a "clean" browser context per job application.

  3. BEHAVIORAL PATTERN (this is where the user's traverse-then-apply
     idea lives — it helps here, but only here, and only if randomized)
     - Two-phase design, as the user proposed: a "traverse" pass collects
       new job postings + application links into DynamoDB; a separate
       "apply" pass, run later, walks that queue and submits. This
       breaks the naive search->apply->search->apply loop signature.
     - The traverse pass itself must ALSO be throttled — rapid-fire
       pagination through search results is a bot signal on its own,
       separate from applying.
     - The gap before applying must be RANDOMIZED, not fixed. A flat
       "always 5-10 minutes" is itself a detectable pattern. Use a wide
       randomized jitter (e.g. uniform or log-normal across a few minutes
       to tens of minutes), and occasionally vary further (skip a job,
       batch two applies close together sometimes) so there's no single
       learnable interval.
     - The apply action itself should not be an instant jump from
       "stored link" to "form submitted." Simulate a normal visit first:
       open the job page, scroll/dwell for a realistic amount of time
       (~15-45s, randomized), then proceed to apply — mirrors how a human
       actually reads a posting before applying.
     - Vary run times day to day (don't run the exact same clock schedule
       every single day forever — humans don't job-hunt on a perfect
       schedule).

  4. VOLUME (matters on top of all the above, even if 1-3 are perfect)
     - Hard daily cap per site, configurable, conservative default (start
       low, e.g. 10-15/day, raise only after weeks of stable runs).
     - Weekly cap as a second ceiling, in case daily caps get raised too
       aggressively over time.

  5. CIRCUIT BREAKER (last line of defense when 1-4 aren't enough)
     - On any block/CAPTCHA signal, stop that site's automation
       immediately, log it as "blocked", and cool down for a configurable
       window (hours, not minutes) before trying that site again.
     - Never retry a block in a tight loop.
     - Treat "failed - blocked" as a distinct, prominent status on the
       dashboard so the user always knows if a site has started blocking
       them, and can log in manually to check/clear any challenge.

  Never share/commit storage_state.json (equivalent to a live login).

  Net effect: this reduces risk substantially but does not eliminate it.
  Full-auto submit always carries some residual chance of a temporary
  block or CAPTCHA wall — the user has accepted that tradeoff.
